# Local WSL reliability audit — 2026-09-24

Baseline: `7f599231` plus this patch. Scope: Windows UI / WSL execution boundaries, Board navigation, Automation discovery and launch. Current source was used because the graph predates source-layout changes. No live Windows/WSL or authenticated provider acceptance is claimed.

## Fixed findings

| Finding | Fix and regression evidence |
| --- | --- |
| Healthy project/session switches publish `connecting` and insert a layout-shifting banner | Check bridge readiness before changing host state; keep healthy folder validation out of the banner. WSL/helper-hook tests cover warm validation, generation changes, cold/retry states and content stability. |
| Failed folder validation marks other projects on the same distribution offline | Recheck bridge health on failure; retain the originating folder error without marking a healthy host offline. Stale results remain guarded. |
| Badge probes can overwrite an active connection with false offline state | Skip the competing health probe while connection owns status. Covered by the badge regression. |
| Automation models/defaults/settings/labels use native catalogs | Pass the effective project/worktree directory to existing catalog APIs. Connect and validate before editor discovery, ignore abandoned results, expose errors/retry. |
| Changing an Automation project retains its previous existing worktree | Clear the old worktree association on explicit project change. Preserve saved model IDs during discovery; require selection when the loaded catalog proves a model unavailable. |
| Background Automations depend on the visible session to connect WSL | Validate the actual target before creating a session or dispatching. Failed/canonical-path-mismatched connections fail the run without dispatch. |
| Session initialization substitutes project-catalog defaults for worktree models | Preserve explicitly saved model/settings. `automationLaunch.test.ts` exercises the production callback with an undiscovered worktree model and connection failure. |
| Renamed-project lookup uses native metadata for WSL paths | Use the existing guest read channel and distribution-qualified Linux device/inode identities. Sibling lookup is capped at 20,000 entries. Production Rust/Python fixtures cover Unicode renames, absent identities and wrong-distribution identities. |

This is a task-directed audit across integration boundaries, not proof that every provider/platform combination is defect-free.

## Validation

- `npm run check:web`: **4,065 passed, 16 skipped**, 354 passing / 4 skipped files; TypeScript passed.
- `npm run check:rust`: formatting and Clippy passed; **537 passed, 3 ignored**. Ignored checks require a release benchmark, authenticated Muse, or a native macOS power assertion query.
- Further warm-catalog and project-change assertions passed in the two affected suites: **15 tests**.
- Final WSL-only launch/model-validation scoping preserved native behavior; the affected Automation/launch suites passed again (**6 tests**) and TypeScript passed.
- Actual Automation React UI in Chromium with mocked Tauri: opened the model menu, observed only the Ubuntu fixture model, switched projects, then observed only the Debian fixture model. The browser fixture mounted the actual view directly; the full app shell requires native Tauri.
- Actual Board plus shared hook in Chromium, mocked 180 ms folder validation: **8 warm switches, 218 frames, zero connecting-banner frames, constant Board top position, same Board DOM node**. This is layout regression evidence, not real WSL latency.
- `git diff --check` passed. No release CPU/RSS or live Windows performance measurements.

## Compatibility and remaining acceptance

No public Tauri command signature, session schema, credential location or Automation storage shape changed. `resolve_project_location` gains an internal guest operation. Native identities are unchanged. Existing WSL identities are recaptured when the original folder exists; an already-renamed folder with only an old native identity is not guessed and must be reopened explicitly.

Still unverified: Windows/ConPTY job control, actual WSL shutdown/reboot/reconnect, authenticated provider discovery/resume, approvals, real cancellation/process cleanup, Windows networking and packaged performance. Use the disposable-repository scenarios in [WSL.md](../WSL.md) for live acceptance.

Existing limits remain: OpenCode HTTP/SSE is unavailable in WSL; localhost forwarding depends on Windows/WSL networking; abrupt app exit is not durable Linux supervision. Search uses Linux `git grep`; the shared non-Git fallback is literal-only (regex fallback currently returns no matches). No new search engine or provider transport was added.
